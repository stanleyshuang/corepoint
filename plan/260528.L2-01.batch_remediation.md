# L2-01 批次修復時限政策調整分析

- **L2-01 目標版本**：v1.0
- **MS Word 格式基準**：`template/文件管制程序2.7.doc` 定義受控程序文件邏輯；`template/樣本.docx` 定義實際字型、字級與段落樣式。

## 1. 背景與目標

隨著 AI 輔助弱點挖掘、掃描與 PoC 產生能力提升，公開 CVE、第三方元件弱點與研究員通報數量預期會增加。若所有案件均套用高頻率更新與短週期修補要求，將對 RD、DQV/QA、PM 與 PSIRT 形成不可持續的工作量壓力。

本次調整目標是：在不降低 CRA、已遭利用、疑似遭利用、安全或營運高衝擊案件處理時限的前提下，允許「公開 CVE 但沒有立即通報必要」之案件採取風險分級與批次修復，以定期安全更新、整合式公告或下一版維護版本方式處理。

## 2. 已確認事實

1. 現行 `doc/L2-01_vulnerability-handling-and-disclosure-process.md` 已在 `8.2 時限政策` 明定：
   - CRA / 已知遭利用 / 安全或營運高衝擊案件，即 E3/E2 事件：
     - 收件確認：24 小時內
     - 初步分流 / 可重現性判斷：1 至 3 個工作日
     - 狀態更新：每 1 至 3 個工作日一次
   - Critical 案件狀態更新：
     - 收件確認：1 個工作日內
     - 初步判斷：3 至 5 個工作日
     - 狀態更新：每 5 個工作日一次
   - 其他案件狀態更新：
     - 收件確認：3 個工作日內
     - 狀態更新：每 5 個工作日一次
2. 現行 `7.6 修補時程基準` 已允許：
   - `Critical`：30 至 90 天內完成修補或有效緩解方案。
   - `High / Medium`：3 至 6 個月或併入下一重大版本。
   - `Low`：依產品生命週期與維護計畫排程，可併入例行維護。
3. 現行 `7.4 已遭利用狀態判定` 已將 E0/E1/E2/E3 作為優先級、通報、揭露與修補時程依據。
4. 現行 `7.8 揭露與通知決策` 已允許 Medium/Low 弱點於完整解決方案就緒後採整合式公告。
5. `template/文件管制程序2.7.doc` 為 Word 97-2003 格式文件；目前可確認其 6.4.2 指向二階文件 QP 編號邏輯，6.5 指向文件編寫注意事項，包含章節階層、版次遞增與參照格式。
6. `template/樣本.docx` 的有效樣式字級應嚴格維持 12pt；已確認 `Normal`、`H1`、`H2`、`H3`、`H4`、`H5`、`List Paragraph`、`Body`、`Body EN`、`H2_EN`、`H3_EN`、`H4_EN` 與 `H5_EN` 均為 12pt 或繼承 12pt。

## 3. 合理假設

1. 「公開之 CVE，但沒有立即通報必要」係指：
   - 已有 CVE 或公開弱點資訊；
   - 尚無可靠證據顯示 IEI 產品遭主動利用；
   - 未觸發 CRA Article 14、官方 CERT/CSIRT 緊急協調、客戶合約即時通知或主管機關強制通報；
   - 經產品影響分析後，風險不屬 E2/E3 或安全 / 營運高衝擊案件。
2. 批次修復不代表不處理，而是將多個相近風險、相近元件或相近產品線之弱點納入同一 remediation batch、maintenance release 或安全更新週期。
3. 若批次期間出現 exploit、CISA KEV 收錄、客戶實際受害、官方通報、CRA 觸發訊號或風險升級，案件應退出批次池並轉入加速處理。

## 4. 風險判斷

| 影響面 | 風險 | 判斷 |
|---|---|---|
| 法遵與 CRA | 若批次修復被誤用於 E3 或 severe incident，可能延誤 24/72 小時通報 | 必須明確排除 CRA、E2/E3、severe incident 與法定通報案件 |
| RD 工作量 | 若每個公開 CVE 都單案即時修補，可能造成 RD 上下文切換與 release 壓力 | 批次修復可降低重工與測試成本 |
| 客戶風險 | 若公開 CVE 長時間無狀態更新，客戶可能誤判 IEI 未處理 | 應保留批次追蹤、下一次更新時點與必要 workaround |
| 稽核證據 | 批次處理若無 Jira 留痕，可能無法證明風險接受與處理依據 | Jira 應記錄修復 Jira ID、批次納入理由、排除緊急通報依據、預計 release window |
| 揭露一致性 | 多 CVE 批次公告可能造成受影響產品、版本與修補說明混亂 | 應要求公告表格化列出 CVE、產品、版本、修補 / 緩解方式 |

## 5. 建議採用的最小修改策略

不建議大幅重寫整份 L2。內容面建議以最小修改方式補強 4 個區塊；Word 產出面需同步調整轉換 workflow 與 build scripts，避免批次修復政策文字完成後，DOCX 輸出不符合受控文件格式。

1. `7.5 修補或緩解規劃`
   - 新增批次修復適用條件與退出條件。
2. `7.6 修補時程基準`
   - 明確定義公開 CVE、無立即通報必要案件可併入定期批次修復。
3. `8.2 時限政策`
   - 保留 E2/E3 / CRA 高頻更新不變。
   - 新增「公開 CVE 但無立即通報必要」之更新節奏。
4. `10.1 必填紀錄` 與 `11 稽核與量測`
   - 補修復 Jira ID、批次修復決策、退出批次原因、批次修復完成率等留痕與指標。
5. `prompt/workflow/markdown_convert_msword.md` 與 `build/`
   - 依 `template/文件管制程序2.7.doc` 補入二階文件與文件編寫規則。
   - 依 `template/樣本.docx` 強制 H1/H2/清單段落/本文/英文樣式有效字級為 12pt。
   - 修正英文樣式名稱為 `Body EN`、`H2_EN`、`H3_EN`、`H4_EN`、`H5_EN`，避免腳本使用不存在的 `H2EN`、`BodyEN` 造成格式回退。
   - Mermaid 圖片替代時不得額外新增「流程圖 / Flow Chart」標題。

## 6. 建議修改文字

### 6.1 建議修改 `7.5 修補或緩解規劃`

建議於第 7.5 節第 3 點後新增：

```markdown
4. 對於已公開 CVE 或第三方元件弱點，若經 PSIRT、PM 與 RD 初步判定未觸發 CRA Article 14、非 E2/E3、無已知在野利用證據、無重大客戶或營運高衝擊，且已有可行監控或暫行緩解方式者，得納入批次修復規劃。批次修復應明確記錄修復 Jira ID、預計修復或維護版本、下一次檢視日期與退出批次之觸發條件。
5. 若批次修復案件於處理期間出現 exploit 活動、CISA KEV 收錄、官方 CERT/CSIRT 緊急通知、客戶實際受害、CRA 觸發訊號、CVSS / EPSS 或產品風險顯著升高，PSIRT 應重新分級並視需要退出批次修復，轉入加速修補、客戶通知或 CRA 通報流程。
```

原第 4、5 點需順延為第 6、7 點。

### 6.2 建議修改 `7.6 修補時程基準`

建議將現行文字：

```markdown
- `High / Medium`：3 至 6 個月或併入下一重大版本。
- `Low`：依產品生命週期與維護計畫排程，可併入例行維護。
```

調整為：

```markdown
- `High / Medium`：3 至 6 個月、下一重大版本或經核准之批次安全更新。
- `Low`：依產品生命週期與維護計畫排程，可併入例行維護或批次修復。
```

並於該節末新增：

```markdown
對於公開 CVE、供應商公告或弱點資料庫發現之案件，若無立即通報必要且未符合 E2/E3、CRA、重大客戶風險或安全 / 營運高衝擊條件，得依風險、產品線、元件來源、release feasibility 與測試資源納入批次修復。批次修復不得作為延後處理高風險或法定通報案件之理由。
```

### 6.3 建議修改 `8.2 時限政策`

現行 E2/E3 / CRA 行應保留不變，但建議修正文句中的重複與標點：

```markdown
| 適用於 CRA / 已知遭利用 / 安全或營運高衝擊案件（即 E3/E2 事件） | 收件確認：24 小時內，初步分流 / 可重現性判斷：1 至 3 個工作日，狀態更新：每 1 至 3 個工作日一次 | 直到修補或暫時緩解就緒 |
```

建議於 Critical 案件與其他案件之間新增：

```markdown
| 公開 CVE 但無立即通報必要之批次修復案件 | 收件確認：3 個工作日內，初步分流 / 是否納入批次判斷：10 個工作日內，狀態更新：依批次週期或至少每 30 日一次 | 僅適用於非 E2/E3、非 CRA、無重大客戶或營運高衝擊之案件；若風險升級，應退出批次並改依高風險時限處理 |
```

若文件擁有者希望更保守，可將 `10 個工作日內` 改為 `5 至 10 個工作日內`，或將 `至少每 30 日一次` 改為 `每 15 至 30 日一次`。

### 6.4 建議修改 `7.8 揭露與通知決策`

建議將現行：

```markdown
3. Medium/Low 弱點得於完整解決方案就緒後採整合式公告。
```

調整為：

```markdown
3. Medium/Low 弱點或經核准之批次修復案件，得於完整解決方案、維護版本或批次安全更新就緒後採整合式公告；公告仍應清楚列出 CVE、受影響產品 / 版本、修補或緩解方式、發布日期與必要限制。
```

### 6.5 建議修改 `10.1 必填紀錄`

建議於必填紀錄中新增：

```markdown
- 是否納入批次修復、Jira ID、批次納入理由、預計 release window、下一次檢視日期與退出批次條件。
```

### 6.6 建議修改 `11 稽核與量測`

建議於指標清單新增：

```markdown
- 批次修復案件數、批次修復完成率、平均批次週期、退出批次轉高優先處理案件數。
- 公開 CVE 初步分流完成時間與批次納入判定時間。
```

## 7. 對下階文件的影響

建議後續 L3 文件補充下列操作細節，不必全部放入 L2：

1. 批次修復 Jira workflow：
   - `Candidate for Batch Remediation`
   - `Batch Assigned`
   - `Scheduled for Maintenance Release`
   - `Removed from Batch / Escalated`
   - `Batch Released`
2. 批次修復欄位：
   - 修復 Jira ID
   - CVE ID
   - upstream supplier
   - affected product / version
   - risk rating
   - exploitation status
   - CRA applicability
   - planned release window
   - next review date
   - escalation trigger
3. 批次審查節奏：
   - 建議 PSIRT / PM / RD / DQV 至少每月檢視一次 batch backlog。
   - 高暴露產品線或高 CVE 密度期間，可提高為每兩週一次。
4. 公告模板：
   - 支援多 CVE、多產品、多版本表格。
   - 每筆 CVE 應列明修補版本、workaround、是否需重開機、是否有相容性限制。

## 8. 不建議修改的內容

1. 不建議降低 CRA、E2、E3、severe incident 或安全 / 營運高衝擊案件之 24 小時收件確認、1 至 3 個工作日初步分流與 1 至 3 個工作日狀態更新要求。
2. 不建議把所有公開 CVE 一律視為批次修復；仍需先完成產品影響分析、Exploitation Status 初判與 CRA 適用性判定。
3. 不建議在 L2 中指定固定每月或每季 release 日期；實際 release calendar 應由 L3、安全更新管理程序或產品線維護計畫定義。
4. 不建議以批次修復取代 workaround 或客戶預通知；若客戶有立即風險，仍應提供暫行風險降低措施。
5. 不建議讓 DOCX 生成腳本自行推導或覆蓋 Word 樣本樣式；樣式應以 `template/樣本.docx` 為準，文件管制邏輯才以 `template/文件管制程序2.7.doc` 為準。

## 9. 最小修改結論

本次需求可用小範圍文字補強完成，不需改變 L2 主流程架構。核心原則為：

1. 高風險快速通道不變：CRA、E2/E3、severe incident、安全或營運高衝擊案件仍維持現行快速時限。
2. 公開 CVE 可批次化：非 E2/E3、非 CRA、無立即通報必要且無重大客戶或營運高衝擊者，可納入批次修復。
3. 批次修復需可稽核：每筆案件仍需 Jira 留痕、修復 Jira ID、納入理由、檢視頻率、退出條件與完成證據。
4. 風險升級需退出批次：一旦出現利用、官方緊急通知、客戶受害或 CRA 觸發訊號，應重新分級並切換為加速處理。

建議下一步依第 6 節文字修改 `doc/L2-01_vulnerability-handling-and-disclosure-process.md`，並同步補入 `prompt/translation/translation_memory_l2_01.json`，避免後續 DOCX 生成因新增中文缺少英文對照而中止。
