已確認事實


prEN 40000-1-3 是針對 products with digital elements 的 vulnerability handling 要求文件，流程涵蓋 Applicability、Preparation、Receipt、Verification、Remediation、Release、Post-release。

L2-01 目前已有弱點受理、ACK、驗證、修補、揭露、CRA 通報、Jira 留痕、Exploitation Status E0-E3、資料保存與稽核指標。

gap analysis 指出的主要缺口集中於 SBOM/HBOM、定期 security test/review、EUVD/監控來源、machine-readable advisory、post-release remediation monitoring。


prEN 文件性質分析

就 ISO 9000 文件階層觀點，prEN 40000-1-3 本身不是 IEI 內部二階或三階文件，而是外部要求標準。

若要映射到 QMS 文件層級，它比較接近「二階程序書的要求來源」或「程序要求框架」，原因是它定義流程階段、必要活動、輸入、輸出、要求與稽核證據，但不規定 IEI 內部實際表單、Jira 欄位、掃描工具、操作步驟或責任人姓名。

其中 SBOM 產製、HBOM 欄位、EUVD 監控頻率、CSAF 產出、Jira workflow 等細節，則應轉化為三階作業文件或表單。

L2-01 內容檢視

從弱點處理與揭露程序角度，L2-01 主流程完整，且 E0-E3 與 CRA 通報判定寫得有實務價值。主要缺漏不是「案件流程」，而是「準備能力」與「發布後持續監控」仍不足。

從二階程序書角度，目前適合保留在 L2 的內容包括：流程階段、角色責任、受理時限、風險分級原則、CRA 升級條件、揭露決策原則、Jira 留痕要求、稽核與保存要求。

較適合下放 L3 的內容包括：具體 Jira 欄位名稱、附件命名、IOC/log 模板、SBOM/HBOM 欄位格式、監控清單逐項來源、CSAF/CVE/EUVD 操作步驟、security test/review checklists。

風險判斷

若 L2 不補上述治理要求，未來稽核時可能被認定只有「案件處理流程」，但無法證明具備 prEN 要求的準備、監控、元件識別、定期測試、發布格式與發布後監控能力。

但若把 SBOM 欄位、CSAF JSON、Jira workflow 都寫進 L2，文件會過度操作化，後續工具或流程變更會造成程序書頻繁改版。


建議行動

建議下一步先同意 L2 補強範圍：我會只把「必須留在二階」的治理要求加入 L2，並在文字中明確指向 L3 作業文件承接細節。等你確認後，我再實際修改文件。


可優化之處

可省略或不需要特別指定的內容：L2 不需要列出每個 SBOM 欄位、Jira 欄位名稱、掃描工具名稱、CSAF JSON 範本。

需要補充或更精確描述的規格：IEI 是否正式將 prEN 40000-1-3 作為符合性目標、哪些產品適用 CRA、SBOM/HBOM owner、EUVD/CSAF 是否要納入 2026 或 2027 目標。

可提升品質的建議：建立一份 L3 對照文件，專門承接 SBOM/HBOM、監控來源、Jira workflow、CSAF/EUVD/CVE 發布、security test/review plan。
